# Which Bench — benchmark identity and interpretation

Snapshot: September 29, 2026. This is the research layer for the recurring benchmarks in the release inventory. It describes what is being measured and what must be recorded before treating two mentions as comparable. A benchmark name alone is not a comparable score.

## Identity rule

Store **family, version, split/task snapshot, metric, agent harness, tools, effort/budget, number of attempts, safeguards/fallbacks, evaluator, and evaluation date** separately. The raw label in the source stays immutable. `SWE-bench Verified`, `SWE-Bench Pro (Public)`, and `SWE-Bench Pro V2` are three distinct tests. `Terminal-Bench 2.1` is a changed task release of 2.0, while 3.0 and 4.0 alter the difficulty distribution. If the details are absent, use `unknown`, not a guessed default.

## Extraction rules for the implementation

1. One **release event** can have several model variants, one shared blog, and one shared card. Store artifact IDs independently from model IDs; a benchmark in a shared article is not automatically a claim about every variant.
2. For a launch post, count a benchmark only when its name is in selectable prose, a native HTML table, or an accessible caption. An image's alt description and an image-only chart are excluded under the requested rule. Store `narrative`, `table`, and `caption` separately.
3. For a model/system card, count names from readable card text and tables. Store the card version or retrieval date; cards can be revised. Record the section and page, not just presence. Do not infer an unstated coding score from a safety-system card.
4. Record **literal label** and a conservative canonical family. A bare `Terminal-Bench` does not imply 2.0; a bare `GDPval-AA` does not imply v2. Keep unknown fields unknown.
5. Separate a score **reported by the lab** from one **measured by a benchmark owner**, and preserve the latter's methodology changes. Never rank models by mixing scores across benchmark versions, harnesses, budgets, subsets, or fallback policies.

## Research limits

Some named evaluations are proprietary or described only inside a lab's card (for example, internal expert coding tasks and specialized cyber tests). Their task sets may not be independently inspectable. The inventories preserve their names as claims in the source; they are not endorsements of validity. The glossary prioritizes benchmark families that recur across releases or bear directly on coding and agent work.
